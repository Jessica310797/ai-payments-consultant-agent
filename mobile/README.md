# PayNavigate — mobile app

An Expo (React Native) payments intelligence app for Australian merchants. It has the same design and numbers as the
web dashboard in [`../dashboard`](../dashboard). Both use the calculations and demo data in [`../shared`](../shared).

**Tabs:** Home (dashboard), Transactions, Audit, October, More.

- **Home** - cost summary with a Month / 3 months / 6 months switch and the cost trend, October changes, top cost
  drivers, audit analysis and ranked next actions. Every card opens a detail screen.
- **Audit → Upload data** - three ways to add a merchant's data:
  1. **Photograph a statement** (or choose its PDF) and tick that the merchant agreed to share it. Claude reads it on the
     server, you check and correct the figures, then see the **1 October impact** (Today / 1 Oct / + routing and the
     surcharge impact). **Add to dashboard** puts the statement's figures into Home, Costs and Audit. Checked
     statements are saved **on the phone only** (More → Statement checks).
  2. A **transactions CSV**, read on the phone.
  3. A **fee invoice** and its total, to reconcile against transaction fees.
- Until real data is added the app shows **demo data** for a fictional merchant, labelled as such on every screen.

The app never holds the Anthropic API key. It sends statements to the API in [`../api`](../api), which asks Claude to
read them and runs the same 1 October calculations as the website ([`../payments_core.py`](../payments_core.py)).

## Code

| Path | What it is |
| --- | --- |
| `src/app/(tabs)/` | The five tabs |
| `src/app/costs.tsx`, `drivers.tsx`, `finding/[id].tsx`, `change/[id].tsx`, `actions.tsx`, `action/[id].tsx` | Detail screens |
| `src/app/upload.tsx`, `capture.tsx`, `check.tsx`, `results.tsx`, `statements.tsx` | Adding data, and the statement flow |
| `src/app/search.tsx`, `notifications.tsx`, `settings.tsx` | Header icons and settings |
| `src/components/` | UI kit (`ui.tsx`), dashboard sections, charts |
| `src/lib/data.tsx` | App data: loads the dataset, selected period, uploads, action status |
| `src/lib/api.ts`, `storage.ts`, `store.tsx` | Statement API calls, saved checks, the statement in progress |
| `../shared/` (imported as `@shared/...`) | Calculations, types, demo data and their tests |

`metro.config.js` adds `../shared` to Metro's watch folders, and `tsconfig.json` maps `@shared/*` to it.

Run `npm install`, then `npm run typecheck`. Server tests: `pip install -r api/requirements.txt pytest httpx`, then `python -m pytest api/tests` (from the repository root). `npx expo start` runs it in Expo Go on your phone for development.
Calculation tests: `cd ../shared && npm install && npm test`.

## Getting it onto phones and into the stores

### 1. Put the API online (Railway)

Use the same Railway account as Pakka - this is a separate service and doesn't touch Pakka.

1. In Railway: **New → Deploy from GitHub repo** → pick `ai-payments-consultant-agent`. Railway reads
   [`railway.json`](../railway.json) and builds [`api/Dockerfile`](../api/Dockerfile).
2. Open the new service → **Variables** and add:
   - `ANTHROPIC_API_KEY` - your Anthropic key (and `ANTHROPIC_WORKSPACE_ID` if your key needs one)
   - `APP_ACCESS_KEY` - any long random string (e.g. generated by a password manager); the app sends it with
     every request
   - `ADMIN_KEY` - another long random string (different from the access key); lets you create merchants and
     invite codes with `api/admin.py`. Keep it to yourself - it isn't in the app.
   - optional `READS_PER_HOUR` - statement reads allowed per logged-in merchant per hour (default 30)
3. Add the accounts database: in the Railway project, **New → Database → Add PostgreSQL**. Then in the API
   service's **Variables**, add `DATABASE_URL` and set it to the reference `${{Postgres.DATABASE_URL}}` (Railway
   offers it in the variable's dropdown). Without it the server uses a temporary file and every redeploy would
   wipe all accounts. The tables are created automatically on first start.
4. **Settings → Networking → Generate Domain**. Note the address (e.g.
   `https://payments-consultant-api.up.railway.app`); `/health` on it should show `{"ok":true}`.

Railway redeploys automatically when `api/` or `payments_core.py` change on `main` (not for website-only changes).

### Merchant logins

The app opens on a **Log in** screen. Accounts are **invite only**: there's no public sign-up.

1. Create the merchant and an invite code (in a Codespace terminal, from the repository root):
   ```
   export PAYNAVIGATE_API=https://ai-payments-consultant-agent-production.up.railway.app
   export ADMIN_KEY=...the ADMIN_KEY from Railway...
   python api/admin.py new-merchant "Corner Bakery"          # prints the merchant's id, e.g. 3
   python api/admin.py invite 3 owner@cornerbakery.com.au    # prints a code like K7QWX-3MZPA
   ```
   Leave the email off to make a code anyone at that business can use. Codes work once and expire after 14 days.
2. Send the merchant the code. In the app they tap **Have an invite code? Create your account**, enter the code,
   their email and a password (at least 10 characters).
3. **Forgotten password:** `python api/admin.py remove-user owner@cornerbakery.com.au`, then send a new invite.
4. `python api/admin.py merchants` lists merchants and how many logins each has.

What a logged-in merchant sees: their business name and **their own data** - statements they photograph and files
they upload - kept on their phone under their account. Until they add some, the dashboard is empty, with an option
to explore the **demo data** (a fictional merchant). Statement reading on the server needs a login, so the shared
access key alone no longer lets anyone use it. Merchants can log out or **delete their account** under More → Account
(Apple requires in-app account deletion).

Passwords are stored as salted scrypt hashes; sessions last 30 days and are stored hashed, so they can be revoked.

### 2. Build for iPhone and send to TestFlight (in a GitHub Codespace, like Pakka)

The server address is already in the app (`eas.json` and `app.json`). The access key isn't in the code - add it on
expo.dev in step 4.

1. On the repository's GitHub page: **Code → Codespaces → Create codespace on main**, then in its terminal:
   `cd mobile && npm ci`
2. `npx eas-cli@latest login` - the same Expo account as Pakka.
   (The app is now called PayNavigate: slug `paynavigate`, bundle ID / package `com.jessicaculnane.paynavigate`.)
3. `npx eas-cli@latest init` - creates the Expo project and adds its ID to `app.json`. Commit and push that change
   (Source Control panel → Commit → Sync).
4. On expo.dev → this project → **Environment variables** → add `EXPO_PUBLIC_APP_ACCESS_KEY` with the same value as
   `APP_ACCESS_KEY` in Railway, for the **production** and **preview** environments (visibility Plain text or
   Sensitive - not Secret, because the app needs to read it).
5. `npx eas-cli@latest build --platform ios --profile production --auto-submit` - log in with your Apple Developer
   account when asked and let EAS create the certificates and the App Store Connect app. When the build finishes it's
   uploaded to **TestFlight**; install it from the TestFlight app on your iPhone (Apple's processing takes 10-30 min).

Android, when you want it: `npx eas-cli@latest build --profile preview --platform android` gives an APK link to
install directly.

### 4. Publish

- **App Store:** in App Store Connect, add screenshots, a description, a **privacy policy URL**, and the App Privacy
  answers (the app uploads photos/documents to your server for processing; it doesn't track users). Give the reviewer
  a sample statement to try. Then submit for review.
- **Google Play:** create a Play Console account (US$25 one-off). New personal accounts must run a **closed test with
  at least 12 testers for 14 days** before they can publish to everyone. Build with
  `npx eas-cli@latest build --profile production --platform android`, upload with `eas submit`, and fill in the Data
  safety form (same answers as Apple).

### Before going public

- A privacy policy page (both stores require one): what's collected (statement images/PDFs), that they're sent to
  Anthropic to be read and not stored on the server, and that saved checks stay on the device.
- Merchants' statements and uploads stay on their phone. Storing them on the server is the next step, so they sync
  across devices and survive a phone change.
- The privacy policy should also cover accounts: the email and business name stored on the server, and how to
  delete an account.
