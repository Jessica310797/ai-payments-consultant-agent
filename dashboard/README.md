# Paywise — payments intelligence dashboard

A mobile-first web app for Australian merchants. The home screen is a prescriptive dashboard: what payments cost,
what changed and why, what the audit found, which October changes need checking, and what to do next.

React + TypeScript, Vite, Tailwind CSS, Recharts, Lucide icons.

```
npm install
npm run dev        # http://localhost:5173
npm test           # calculation tests
npm run build      # static site in dist/ (works on any static host - routes use #/...)
```

## Screens

| Route | Screen |
| --- | --- |
| `#/` | Home dashboard |
| `#/costs` | Period comparison, what changed the cost, by fee type / provider, monthly trend |
| `#/drivers` | Cost drivers (doughnut + ranked table) |
| `#/transactions` | Transactions by card type and provider |
| `#/audit`, `#/audit/:id` | Audit findings and their evidence |
| `#/audit/upload` | Upload a transactions CSV or a fee invoice |
| `#/october`, `#/october/:id` | Change log and each change's source, applicability and next steps |
| `#/actions`, `#/actions/:id` | Recommended actions, with a status you can set |
| `#/more`, `#/search`, `#/notifications` | Data source, method notes, preview states; search; alerts |

## Data

All data comes through `src/data/source.ts` → `loadDataset()`. Today it returns the **demo fixtures** in
`src/data/fixtures/` (a fictional merchant, clearly labelled as demo data throughout the app). To use real data,
make `loadDataset()` fetch records with the same shapes (`src/data/types.ts`):

- `LedgerRecord` — one month × provider × card segment: transactions, sales, fees by type, and (optionally) the
  fees the contract says should have been charged. Every figure on the dashboard is calculated from these.
- `RegulatoryChange` — the change log. Regulatory items are marked **To confirm** until checked against the
  official source; the app doesn't assert what the rules are.
- `Invoice`, `Benchmark`, `Merchant`, `Provider` and the routing assumption.

The ledger fixture is generated by `scripts/generate-fixtures.mjs` so the numbers are consistent.

`?demo=loading`, `?demo=empty` and `?demo=error` (or More → Preview states) show the loading, empty and error states.

## How the numbers are worked out (`src/lib/`)

- **Effective cost rate** = total payment costs ÷ payment volume.
- **Changes** compare the selected period (last month, 3 or 6 months) with the period of the same length just before.
- **What changed the cost** (`varianceSplit`) splits the change across each provider × card segment into:
  transaction volume, card mix, contracted pricing changes and an unexplained remainder. The four add up exactly to
  the total change. Without contracted rates, pricing and unexplained are shown together as "rate changes".
- **Audit** (`audit.ts`): *confirmed* discrepancies (charged above contract; invoices that don't match transaction
  fees) are kept separate from *opportunities* (benchmarking, least-cost routing), which are estimates and list their
  assumptions.
- **Recommended actions** (`actions.ts`) are ranked by priority, with impact shown only when the data supports it.

## Uploads

Files are read in the browser and not sent anywhere. Transaction CSVs need date, amount and card scheme columns
(names are matched flexibly; Australian day-first dates; declined/refund rows skipped). Fee columns make the audit
useful. Invoices can be added with their total fees to reconcile them; reading PDFs automatically can be connected to
the existing invoice reader in [`../api`](../api).
